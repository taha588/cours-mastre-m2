N31 — Couche 1, les sources : d'où viennent les données ?

4. La règle

4. C'EST QUOI ? — l'énoncé

Schéma du support (p. 45). La première couche regroupe les systèmes où la donnée naît. Le support en cite six familles :

FamilleExemples du support
ApplicationsERP, CRM, e-commerce
IoTcapteurs, véhicules
APIservices externes
Logsévénements techniques
FichiersCSV, PDF, images
Open Datasources publiques

Question posée par le support. Les sources n'ont ni le même format, ni la même fréquence, ni la même qualité.

5. Explication de la règle

5. L'IDÉE DERRIÈRE LA RÈGLE

Une source est un système qui produit la donnée pour son propre besoin : la caisse enregistre une vente pour encaisser, le capteur mesure une température pour surveiller, le serveur web écrit un log pour se dépanner. Aucune source n'a été conçue pour l'analyse. La couche Sources ne se construit donc pas : elle se constate, et l'architecte doit la décrire avant de décider quoi que ce soit.

Les six familles se distinguent par leur origine. Les applications sont les logiciels de gestion internes (OLTP, N16) ; l'IoT regroupe les objets physiques qui mesurent ; les API donnent accès à des services externes (un transporteur, la météo) ; les logs sont les traces techniques laissées par les systèmes ; les fichiers sont des documents déposés tels quels ; l'open data vient d'organismes publics.

Trois axes les décrivent. Le format dit comment la donnée est organisée : structurée, semi-structurée ou non structurée (N2). La fréquence dit à quel rythme elle arrive : en continu, par lots, ou une fois de temps en temps. La qualité dit à quel point on peut s'y fier : complétude, exactitude, fraîcheur (N25). Le message de la page est que ces trois axes varient d'une source à l'autre.

Pourquoi le support le pose en « question ». Puisque les sources diffèrent sur les trois axes, aucune règle unique ne peut les faire entrer, les stocker et les nettoyer. Le format décidera du stockage (N33), la fréquence décidera de l'ingestion (N32), la qualité décidera des traitements (N34). La description des sources commande donc toute la suite.

CAS PARTICULIERS ET PIÈGES
  • Croire que les sources appartiennent à l'équipe data. Elles appartiennent aux métiers ou à des tiers ; on ne peut pas modifier la caisse pour faciliter l'analyse. On s'adapte à la source, ou l'on négocie un contrat de données avec son propriétaire.
  • Associer une famille à un seul format. Une application fournit des tables structurées, mais aussi des commentaires libres ; une API renvoie du JSON semi-structuré ; un fichier peut être un CSV structuré ou un PDF non structuré. Le format se constate source par source.
  • Associer l'IoT au seul streaming. Un capteur mesure en continu, mais un camion sans réseau peut vider sa mémoire en un seul lot à son retour au dépôt.
  • Prendre l'open data pour une donnée fiable par nature. Elle est publique, pas forcément fraîche ni complète ; sa fréquence de mise à jour est souvent mensuelle ou annuelle.
  • Oublier les logs. Ils ne contiennent pas de « données métier », mais ils disent ce que font les clients sur le site (pages vues, paniers abandonnés) et ce que font les systèmes (erreurs) : c'est souvent la source la plus volumineuse.
  • Confondre source et ingestion. L'API est une source quand elle désigne un service externe qui produit la donnée ; « CDC / API » dans N32 désigne la manière de la faire entrer.

خلاصة بالعربية: طبقة Sources هي البلايص فين كتولد المعطيات. الدعامة كتذكر ست عائلات: التطبيقات (ERP، CRM، التجارة الإلكترونية)، IoT (الحساسات، العربات)، API (خدمات خارجية)، Logs (أحداث تقنية)، الملفات (CSV، PDF، صور) و Open Data (مصادر عمومية). الفكرة المفتاح: هاد المصادر ماعندهاش نفس الشكل، ولا نفس الوتيرة، ولا نفس الجودة. الشكل كيحدد التخزين، الوتيرة كتحدد طريقة الإدخال، والجودة كتحدد المعالجة. داكشي علاش وصف المصادر هو أول خطوة فالهندسة.

6. Le problème que cette règle traite

6. LE PROBLÈME TRAITÉ

L'enseigne veut un tableau de bord qui croise les ventes, la météo et les avis clients. Le premier projet branche les trois sources avec le même script nocturne : les ventes arrivent bien, mais l'API météo limite le nombre d'appels et renvoie des erreurs, les avis clients sont des textes libres que le script tronque, et les capteurs des chambres froides, ajoutés ensuite, envoient une mesure par minute qu'un traitement nocturne ne sait pas exploiter à temps.

Le problème traité par N31 : connaître chaque source avant de la brancher — son format, sa fréquence, sa qualité — au lieu de traiter toutes les sources comme si elles se ressemblaient.

7. À quoi elle va nous servir

7. L'UTILITÉ PRATIQUE

Dresser l'inventaire des sources. Une fiche par source, avec sa famille, son propriétaire et ses trois axes.

Préparer le choix de l'ingestion. La fréquence de la source et la latence demandée par ses consommateurs désignent le batch, le streaming ou le CDC / API (N32).

Préparer le choix du stockage. Une source non structurée (PDF, images, avis) ne va pas dans une table d'entrepôt : elle demande un lac ou un lakehouse (N11, N12, N33).

Anticiper les traitements. Une qualité faible annonce du nettoyage, du dédoublonnage, des contrôles (N25, N34).

Évaluer le risque. Données personnelles, dépendance à un fournisseur externe, limite d'appels d'une API : la couche transverse commence dès la source (N30).

8. D'où vient cette règle

8. D'OÙ ELLE VIENT — la justification

Première raison : les sources sont faites pour opérer, pas pour analyser. C'est le constat de N9 et de N16 : l'application transactionnelle est optimisée pour enregistrer vite une ligne, pas pour répondre à une question d'ensemble. Ses choix de format et de rythme sont dictés par son métier ; l'architecture les reçoit tels quels.

Deuxième raison : la variété est la cause de la complexité. N4 a montré que la gestion devient complexe par le volume, les silos, la diversité des formats et l'arrivée de l'IA. La page 45 en est la traduction concrète : six familles, donc six façons de produire la donnée.

Troisième raison : chaque axe commande une couche.

Axe de la sourceValeurs possiblesCouche qu'il commande
Formatstructuré, semi-structuré, non structuré (N2)Storage : entrepôt pour le structuré, lac / lakehouse pour le reste (N33)
Fréquencecontinue, par lots, ponctuelleIngestion : streaming, batch, CDC / API (N32)
Qualitécomplète ou lacunaire, exacte ou douteuse, fraîche ou ancienne (N25)Processing : nettoyage, contrôle, enrichissement (N34)

Quatrième raison : on ne corrige pas une source, on la décrit. Comme l'architecte ne maîtrise pas les sources, la seule manière de rester fiable est de savoir exactement ce qu'elles livrent. C'est pourquoi les métadonnées de N26 (propriétaire, description, fraîcheur attendue) commencent à la source.

9. Où l'utiliser

9. OÙ ? — les terrains d'emploi

L'inventaire d'une plateforme de données. Lister toutes les sources de l'entreprise, internes et externes.

Le cadrage d'un nouveau projet. Avant un tableau de bord ou un modèle, identifier les sources nécessaires et vérifier qu'elles existent avec la bonne fréquence.

La négociation avec les propriétaires. Fixer avec le métier ou le fournisseur un contrat : format, rythme, qualité minimale, préavis en cas de changement.

L'audit de conformité. Repérer les sources qui contiennent des données personnelles ou soumises à licence (open data, API payantes).

Le diagnostic d'un incident. Une valeur fausse se remonte jusqu'à la source qui l'a produite.

10. Quand l'utiliser

10. QUAND ? — les signaux qui la désignent

Au tout début d'une architecture. La couche Sources est la première étape de la démarche de N30.

Quand une nouvelle source arrive. Un nouveau fournisseur, un nouveau capteur, une nouvelle application : on la décrit avant de la brancher.

Quand une source change. Nouvelle version de l'ERP, colonne renommée, API modifiée : la fiche doit être mise à jour, sinon l'ingestion casse.

Quand un même script ne suffit plus. Signe que des sources de formats ou de fréquences différents ont été traitées comme une seule.

Quand un énoncé demande « d'où viennent les données ? ». On répond par les familles de sources et leurs trois axes.

11. Comment l'utiliser

11. COMMENT ? — la démarche pas à pas

Étape 1 — Lister les sources. Partir des usages attendus et remonter vers les systèmes qui produisent la donnée.

Étape 2 — Classer chaque source dans une famille. Application, IoT, API, logs, fichiers, open data.

Étape 3 — Décrire le format. Structuré, semi-structuré ou non structuré, avec un exemple réel d'enregistrement.

Étape 4 — Décrire la fréquence. Rythme de production (par seconde, par jour…) et volume par période.

Étape 5 — Décrire la qualité. Taux de valeurs manquantes, doublons, retards connus, fiabilité du fournisseur.

Étape 6 — Noter le propriétaire et les risques. Qui la gère, données personnelles, limites d'accès. La fiche ainsi remplie sert d'entrée à N32, N33 et N34.

À RETENIR

La couche Sources regroupe les systèmes où la donnée naît : applications (ERP, CRM, e-commerce), IoT (capteurs, véhicules), API (services externes), logs (événements techniques), fichiers (CSV, PDF, images) et open data (sources publiques). Elles n'ont ni le même format, ni la même fréquence, ni la même qualité : les décrire sur ces trois axes commande l'ingestion, le stockage et le traitement.

طبقة Sources فيها الأنظمة اللي كتولد فيها المعطيات: التطبيقات، IoT، API، Logs، الملفات و Open Data. هاد المصادر ماعندهاش نفس الشكل، ولا نفس الوتيرة، ولا نفس الجودة؛ ووصفها على هاد المحاور الثلاثة هو اللي كيحدد الإدخال، التخزين والمعالجة.

EXERCICE 12.1 — classer les sources de l'enseigne

Rangez chaque élément dans l'une des six familles du support et donnez son format (structuré, semi-structuré, non structuré) : (a) le logiciel de caisse des 120 magasins ; (b) le CRM du programme de fidélité ; (c) les capteurs de température des chambres froides ; (d) le GPS des camions de livraison ; (e) l'API météo ; (f) les journaux du serveur du site e-commerce ; (g) les bons de livraison fournisseurs scannés en PDF ; (h) le recensement de la population par commune publié par l'organisme statistique national.

EXERCICE 12.2 — fréquence et volume de trois sources

Trois sources de l'enseigne. Capteurs : 120 magasins × 4 chambres froides, une mesure par minute, 200 octets par mesure. Caisses : 600 000 tickets par jour, 2 Ko par ticket, envoyés en un lot à 23 h 30. Open data : un fichier de recensement de 50 Mo publié une fois par an. (a) Calculez le nombre de mesures et le volume par jour des capteurs. (b) Calculez le volume par jour des caisses. (c) Laquelle produit le plus de messages, laquelle le plus d'octets ? (d) Qu'en déduire pour l'ingestion ?

CORRIGÉ 12.2

(a) Capteurs. 120 × 4 = 480 chambres froides. Une mesure par minute : 480 × 1 440 = 691 200 mesures par jour. Volume : 691 200 × 200 o = 138 240 000 o ≈ 138 Mo par jour.

(b) Caisses. 600 000 × 2 Ko = 1 200 000 Ko ≈ 1,2 Go par jour, en un seul lot.

(c) Comparaison. Les capteurs produisent plus de messages (691 200 contre 600 000), mais presque 9 fois moins d'octets (138 Mo contre 1,2 Go). L'open data, elle, ne pèse que 50 Mo par an, soit environ 0,14 Mo par jour en moyenne.

(d) Conclusion. Les capteurs envoient un flux continu de petits messages : ingestion streaming (N21). Les caisses livrent un gros lot quotidien : ingestion batch (N20). L'open data se recharge une fois par an : un simple téléchargement planifié. Les trois sources diffèrent bien par leur fréquence, comme l'annonce le support, et c'est cette différence — pas le volume total — qui choisit l'ingestion.

EXERCICE 12.3 — mesurer la qualité d'une source

Le CRM de fidélité contient 400 000 fiches clients. Un contrôle trouve : 60 000 fiches sans téléphone, 24 000 doublons (même client inscrit deux fois), 8 000 dates de naissance impossibles (avant 1900 ou dans le futur). (a) Calculez le taux de chaque défaut. (b) Combien de clients distincts l'enseigne a-t-elle réellement ? (c) Le service marketing veut envoyer un SMS à tous les clients : quelle part de la base est atteignable, en supposant que les fiches sans téléphone et les doublons ne se recoupent pas ? (d) Quel défaut gêne le plus un modèle qui prédit les achats selon l'âge ?

CORRIGÉ 12.3

(a) Taux. Téléphone manquant : 60 000 / 400 000 = 15 %. Doublons : 24 000 / 400 000 = 6 %. Dates impossibles : 8 000 / 400 000 = 2 %.

(b) Clients distincts. Chaque doublon est une fiche en trop : 400 000 − 24 000 = 376 000 clients.

(c) Clients atteignables par SMS. Parmi les 376 000 clients distincts, 60 000 n'ont pas de téléphone : 376 000 − 60 000 = 316 000, soit 316 000 / 376 000 ≈ 84 %. Sans dédoublonnage, on enverrait aussi 24 000 SMS en double.

(d) Pour le modèle. Le téléphone manquant ne gêne pas un modèle d'âge ; ce sont les 2 % de dates impossibles qui faussent la variable utile, et les doublons qui comptent deux fois certains clients. La qualité d'une même source se juge donc selon l'usage (N25) : le défaut le plus grave pour le SMS (15 %) n'est pas celui qui gêne le modèle (2 %).

TRANSITION — vers N32

Une source décrite n'est pas encore une source exploitable : il faut faire entrer sa donnée dans la plateforme, au rythme qui convient. Les caisses livrent un lot, les capteurs un flux, l'ERP des modifications à répliquer. Choisir pour chaque source entre batch, streaming et CDC / API est l'objet de N32.
