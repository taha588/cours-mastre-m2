15. Problèmes du réel

Les trente-cinq notions ont été vues une à une. Un vrai projet ne les présente jamais séparément : il faut, sur le même cas, choisir les sources à capter, le mode d'ingestion, le stockage, les traitements, les consommateurs et la gouvernance, en tenant compte du volume, de la latence et du coût. Les quatre problèmes ci-dessous reprennent l'étude de cas du support (p. 51-56) — dont le sous-titre résume l'esprit : comprendre la transformation par les contraintes — puis reviennent à l'enseigne de la section 2. Chaque énoncé est suivi d'un corrigé détaillé.

Méthode commune. Pour chaque problème : (1) lister ce qui existe (sources, usages) ; (2) nommer les contraintes, chiffres à l'appui ; (3) déduire chaque couche de ces contraintes, jamais d'une préférence technologique ; (4) vérifier qu'aucune copie n'est faite sans raison et que la gouvernance couvre toute la chaîne.

PROBLÈME 1 — Entreprise e-commerce : de l'architecture traditionnelle à l'architecture moderne (p. 52-54)

Une entreprise de e-commerce dispose de sept sources : ERP, CRM, site web, application mobile, paiement, avis clients, logs. Ses usages actuels sont le reporting mensuel, les KPI ventes et l'analyse clients. La direction veut ajouter trois nouveaux usages : un dashboard quotidien, la recommandation de produits et la détection de fraude quasi temps réel.

Aujourd'hui, l'architecture est traditionnelle (p. 53) : les applications métiers (ERP, CRM, site, application mobile, autres applications) écrivent dans une base de données relationnelle centralisée (type Oracle, SQL Server, MySQL), à données structurées, interrogée en SQL ; le reporting (rapports standards, tableaux de bord, analyses descriptives) lit directement cette base.

Données complémentaires : l'historique d'un an pèse 3 000 Go bruts ; le stockage coûte 0,25 DH par Go et par mois.

Question du support : « Quelle architecture faut-il construire pour supporter ces usages sans multiplier les copies ? »

  1. Expliquez les trois problèmes potentiels de l'architecture actuelle et rattachez chacun aux notions du cours.
  2. Classez les sept sources selon leur structure et proposez, pour chacune, un mode d'ingestion.
  3. Proposez une architecture en cinq couches et placez-y chacun des six usages.
  4. Si chaque usage reliait lui-même chaque source, combien de liaisons faudrait-il ? Combien avec l'architecture en couches ?
  5. Si chacun des six usages gardait sa propre copie complète de l'historique, quel serait le coût mensuel ? Comparez avec un socle partagé (3 000 Go bruts + 800 Go conformes + 500 Go de versions prêtes à l'usage).
  6. Que contient la gouvernance transverse, et pourquoi doit-elle couvrir toutes les couches ?
CORRIGÉ DU PROBLÈME 1

1. Les trois problèmes potentiels (p. 53).

  • « Le reporting peut dépendre directement de la base transactionnelle. » Les requêtes analytiques (balayage de millions de lignes) et les transactions (écritures courtes et nombreuses) se disputent la même base : c'est le conflit OLTP / OLAP de N16 à N19. Plus le dashboard devient quotidien, plus il charge la base qui encaisse les commandes.
  • « Les nouvelles sources ne trouvent pas naturellement leur place. » Les événements du site et de l'application, les logs et les avis clients sont semi-structurés ou non structurés (N2) : ils n'entrent pas dans un schéma relationnel fixe, donc on ne les charge pas. C'est la limite qui a fait naître le Data Lake (N11).
  • « L'IA nécessite davantage de données préparées. » La recommandation et la fraude demandent un historique long, des features et des labels (N29) ; la base opérationnelle ne garde que ce qui sert aux transactions et ne prépare rien.

2. Sources : structure et ingestion. Le mode d'ingestion découle de la fréquence à laquelle la source change et de la latence exigée par ses consommateurs (N32).

SourceStructureIngestionRaison
ERPstructuréeCDCtables qui changent par lignes ; on ne recopie que les modifications
CRMstructuréeCDCmême logique ; les suppressions (droit à l'effacement) doivent suivre
Site websemi-structurée (événements JSON)streamingla recommandation exploite la session en cours
Application mobilesemi-structurée (événements JSON)streamingidem

3. Architecture en cinq couches (p. 54).

CoucheContenu dans ce cas
SourcesERP, CRM, site web, application mobile, paiement, avis clients, logs
IngestionCDC (ERP, CRM), streaming (site, application, paiement), batch (avis, logs), connecteurs
StorageData Lake pour le brut de toutes les sources ; Lakehouse / Data Warehouse pour les données conformes (ventes, clients, produits) ; base opérationnelle pour servir scores et recommandations ; gestion des métadonnées
Processingnettoyage (doublons clients), transformation (ventes conformes), enrichissement (paiement + profil client), agrégation (KPI du jour), features (fraude, recommandation), orchestration
Analytics / AIBI, Analytics, Machine Learning, alertes temps réel

Placement des six usages :

  • Reporting mensuel et KPI ventes : BI, sur les agrégats construits à partir des ventes conformes ;
  • Dashboard quotidien : BI, alimenté par un traitement batch nocturne (prêt à 8 h) — le streaming n'apporte rien à un écran lu une fois par jour ;
  • Analyse clients : Analytics (exploration) sur les tables conformes clients et ventes ;
  • Recommandation : ML ; modèle entraîné sur l'historique du lake, features calculées la nuit, complétées par les événements de la session reçus en streaming ;
  • Fraude quasi temps réel : ML + alertes ; le paiement est lu en streaming, enrichi du profil client, scoré, puis la décision est servie par la base opérationnelle.

4. Nombre de liaisons. Point à point, chaque usage relie chaque source : 7 × 6 = 42 liaisons à construire et à maintenir. Avec les couches, chaque source entre une fois et chaque usage lit le socle une fois : 7 + 6 = 13 liaisons. C'est le passage de S × C à S + C vu en N30. Ajouter une huitième source coûte alors une liaison au lieu de six.

5. Coût des copies.

  • Six copies complètes : 6 × 3 000 = 18 000 Go ; 18 000 × 0,25 = 4 500 DH par mois.
  • Socle partagé : 3 000 + 800 + 500 = 4 300 Go ; 4 300 × 0,25 = 1 075 DH par mois.
  • Économie : 4 500 − 1 075 = 3 425 DH par mois, soit 3 425 × 12 = 41 100 DH par an.

L'argent n'est pas le seul gain : avec six copies, il existe six définitions possibles du « chiffre d'affaires » et six dates de fraîcheur. Avec un socle, la version conforme est unique ; seules les versions prêtes à l'usage (agrégats, features) sont propres à chaque consommateur (N35).

6. Gouvernance transverse. Le support la résume en six mots : catalogue, qualité, sécurité, accès, lineage, observabilité (N26). Elle est transverse parce qu'un défaut se crée dans une couche et se voit dans une autre : un doublon client créé à l'ingestion fausse la recommandation en couche 5 ; une donnée de paiement mal protégée dans le lake expose l'entreprise même si le dashboard est correct. Exemples concrets ici : numéro de carte tokenisé dès l'ingestion et jamais stocké en clair ; accès aux avis clients restreint s'ils contiennent des données personnelles ; lineage permettant de propager une demande d'effacement du CRM jusqu'aux features.

PROBLÈME 2 — La grille de décision appliquée chiffres en main (p. 55)

Le support propose sept questions à poser avant toute décision d'architecture :

  1. Quel est le volume quotidien et sa croissance ?
  2. Quel est le délai acceptable entre production et utilisation ?
  3. Quelles sources sont structurées, semi-structurées ou non structurées ?
  4. Quelles données doivent être conservées brutes ?
  5. Quels consommateurs ont besoin de données fraîches ?
  6. Quelles contraintes de sécurité, confidentialité et conformité ?
  7. Quel compromis coût / performance / flexibilité / simplicité ?

On reprend l'entreprise du problème 1 avec les mesures suivantes :

  • événements du site et de l'application : 25 millions par jour, 1 Ko chacun ;
  • logs : 60 Go par jour ;
  • avis clients : 3 000 par jour, dont 10 % avec une photo de 2 Mo ;
  • ERP, CRM et paiement réunis : 1,4 Go par jour ;
  • croissance de l'ensemble : 35 % par an ;
  • besoins de délai : reporting mensuel disponible à J+5 ; dashboard à 8 h pour la veille ; recommandation pendant la session (quelques secondes) ; fraude avant validation du paiement (moins de 1 s).

Répondez aux sept questions, chiffres à l'appui, et tirez de chaque réponse une décision d'architecture.

CORRIGÉ DU PROBLÈME 2

Q1 — Volume et croissance.

  • Événements : 25 000 000 × 1 Ko = 25 000 000 Ko = 25 Go par jour.
  • Photos d'avis : 3 000 × 10 % = 300 photos ; 300 × 2 Mo = 600 Mo = 0,6 Go par jour.
  • Total : 25 + 60 + 0,6 + 1,4 = 87 Go par jour, soit 87 × 365 = 31 755 Go ≈ 31,8 To par an.
  • Dans trois ans : 1,35³ = 2,460375 ; 87 × 2,460375 ≈ 214 Go par jour.

Décision : un stockage objet à séparation stockage / calcul (lake, lakehouse), extensible par ajout de nœuds (scale-out, N15) ; la base relationnelle unique ne peut pas absorber ce volume ni ces formats.

Q2 — Délai acceptable. On applique le critère de N22 : le mode convient si temps de réaction exigé ≥ période de collecte + durée de traitement.

UsageDélai exigéMode retenu
Reporting mensuelJ+5batch mensuel
Dashboard quotidienprêt à 8 hbatch nocturne (fenêtre de plusieurs heures)
Recommandationquelques secondesfeatures nocturnes + événements de session en streaming
Fraude< 1 sstreaming de bout en bout

Décision : deux chemins coexistent, un chemin batch pour la majorité des usages et un chemin streaming réservé aux deux usages qui ne peuvent pas attendre.

Q3 — Structure des sources. Structurées : ERP, CRM, paiement (1,4 Go/j). Semi-structurées : événements, logs (85 Go/j). Non structurées : texte et photos des avis (0,6 Go/j et plus). Le volume non relationnel vaut (85 + 0,6) ÷ 87 ≈ 98,4 % du total. Décision : stockage brut au format d'origine dans le lake ; mise en tables seulement de ce que les usages réclament (N11, N12).

Q4 — Données à conserver brutes.

  • Événements du site et de l'application : oui, car les futurs modèles de recommandation voudront d'autres features que celles d'aujourd'hui (N34 : toute transformation perd de l'information).
  • Paiements : oui, pour l'audit, pour rejouer un modèle de fraude et pour construire les labels (N29).
  • Avis clients : oui, le texte est un corpus réutilisable (analyse de sentiment, GenAI).
  • Logs : brut sur 90 jours puis seulement agrégés : 60 Go/j × 365 ≈ 21,9 To par an pour un usage surtout technique ; le compromis coût l'emporte.

Q5 — Consommateurs de données fraîches. Seuls la fraude (seconde) et la recommandation (session) en ont besoin. Le dashboard quotidien veut des données de la veille, ce qui n'est pas du temps réel. Décision : on ne paie le coût du streaming (état, doublons, heure d'événement, N21) que pour ces deux flux.

Q6 — Sécurité et conformité. Données de paiement : tokenisation à l'ingestion, jamais de numéro de carte dans le lake. Données personnelles du CRM : consentement, droit à l'effacement propagé par le lineage. Avis clients : masquage des noms et adresses avant tout usage GenAI. Accès par rôle à chaque niveau (brut, conforme, prêt à l'usage).

Q7 — Compromis. Tout passer en streaming serait plus « performant » mais plus cher et plus complexe sans bénéfice pour quatre usages sur six. Un lakehouse unique pour le brut et le conforme est plus simple qu'un lake et un warehouse séparés ; on garde un warehouse seulement si la BI exige des performances que le lakehouse n'atteint pas. La flexibilité vient du brut conservé ; la simplicité, du nombre limité de chemins.

Bilan. Chaque question a produit une décision ; aucune n'a été prise par goût pour une technologie. C'est la règle de N6 : l'architecte décide à partir des contraintes, et sait dire pourquoi.

PROBLÈME 3 — TD : architecture IoT / Edge (p. 56)

Énoncé du support :

  • 20 000 capteurs : température, vibration, énergie ;
  • certaines alertes doivent être traitées en moins de 2 secondes ;
  • les historiques sont conservés pour analyse et ML ;
  • certains sites peuvent perdre temporairement la connexion cloud ;
  • concevoir : Edge + ingestion + streaming + stockage + processing + analytics ;
  • bonus : que doit rester local pendant une coupure ?

Hypothèses chiffrées : les capteurs sont répartis sur 40 sites de 500 capteurs ; chaque capteur envoie une mesure toutes les 5 s, de 200 octets. Un aller vers le cloud et retour coûte en temps normal 1,5 s (réseau 0,3 s aller + 0,3 s retour, file d'ingestion 0,5 s, traitement 0,4 s). Une coupure peut durer jusqu'à 6 heures. La liaison montante d'un site est de 10 Mbit/s.

  1. Calculez le débit global (mesures par seconde), le volume par jour et par an.
  2. L'alerte critique peut-elle être calculée dans le cloud ? Justifiez avec le budget de 2 s.
  3. Concevez l'architecture couche par couche.
  4. Quelle taille de tampon local faut-il pour une coupure de 6 h sur un site ? Combien de temps pour rattraper le retard après reconnexion ?
  5. Quels pièges de traitement apparaissent au retour de la connexion ?
  6. Bonus : que doit rester local pendant une coupure ?
CORRIGÉ DU PROBLÈME 3

1. Débit et volume.

  • Débit : 20 000 ÷ 5 = 4 000 mesures par seconde.
  • Par jour : 4 000 × 86 400 = 345 600 000 mesures ; × 200 octets = 69 120 000 000 octets = 69,12 Go par jour.
  • Par an : 69,12 × 365 = 25 228,8 Go ≈ 25,2 To par an, à conserver pour l'analyse et le ML.

2. L'alerte critique dans le cloud ? En temps normal, 1,5 s < 2 s : cela passe, mais avec seulement 0,5 s de marge, qu'un pic de trafic ou une file chargée suffit à consommer. Pendant une coupure, le délai devient infini : l'alerte n'arrive jamais. Une exigence « moins de 2 s » qui doit tenir aussi quand le cloud est inaccessible ne peut donc pas dépendre du cloud. Décision : la détection critique se fait sur une passerelle Edge par site. Budget local : capteur → passerelle 0,05 s, détection 0,1 s, action (alarme, arrêt machine) 0,2 s, soit 0,35 s, avec une large marge.

3. Architecture couche par couche.

CoucheRôle dans ce TD
Sources20 000 capteurs (température, vibration, énergie), un référentiel des machines et des sites
Edge (par site)réception des mesures, règles et modèle d'alerte critique, action locale, tampon horodaté, agrégats locaux
Ingestionstreaming des mesures vers le cloud via un journal rejouable ; envoi par lots du tampon après coupure ; batch quotidien du référentiel
Streamingfenêtres glissantes par capteur (moyenne, écart sur 1 min), détection d'anomalies non critiques, alertes de flotte (plusieurs sites), capteurs muets
Storagelake : mesures brutes partitionnées par date et site ; données conformes et agrégats horaires en lakehouse ; base opérationnelle : dernier état de chaque capteur
Processingnettoyage (valeurs hors plage, doublons), enrichissement (machine, ligne, site), agrégation horaire et journalière, features de maintenance prédictive
Analytics / AIBI (consommation d'énergie par site), Analytics (causes des pannes), ML (prévision de panne à partir des vibrations), alertes
Gouvernancecatalogue des capteurs, qualité (fraîcheur, volume attendu par site), version du modèle déployé sur chaque passerelle (lineage), sécurité des passerelles et des flux

4. Tampon et rattrapage.

  • Mesures d'un site pendant 6 h : 6 × 3 600 ÷ 5 = 4 320 mesures par capteur ; × 500 = 2 160 000 mesures ; × 200 octets = 432 000 000 octets = 432 Mo.
  • Un disque de 64 Go sur la passerelle suffit largement : un site produit 432 ÷ 6 = 72 Mo par heure, donc 64 000 ÷ 72 ≈ 889 h, soit environ 37 jours d'autonomie.
  • Rattrapage : 10 Mbit/s = 1,25 Mo/s ; 432 ÷ 1,25 = 345,6 s ≈ 5,8 min. Le flux courant (72 Mo/h = 0,02 Mo/s) est négligeable devant la bande passante.

5. Pièges au retour de la connexion.

  • Heure d'événement et heure d'arrivée (N21) : 2 160 000 mesures arrivent avec jusqu'à 6 h de retard. Les fenêtres doivent être calculées sur l'heure de mesure, sinon le cloud verra une « explosion » d'activité à la reconnexion et un trou pendant la coupure.
  • Délai de grâce : une fenêtre fermée depuis des heures doit pouvoir être recalculée, ou les mesures tardives doivent être marquées et traitées en batch.
  • Doublons : si la passerelle renvoie un lot dont l'accusé de réception s'est perdu, les mêmes mesures arrivent deux fois. L'ingestion doit être idempotente (N32) : clé unique (capteur, horodatage).
  • Fausses alertes de flotte : un site silencieux pendant 6 h ne doit pas déclencher 500 alertes « capteur muet » ; la règle d'observabilité (N26) doit distinguer un site coupé d'un capteur en panne.

6. Bonus — ce qui reste local pendant une coupure.

  • les règles et le modèle d'alerte critique, dans une version figée et connue du cloud ;
  • les seuils propres à chaque machine et le référentiel minimal du site ;
  • les actions automatiques (alarme, arrêt de sécurité) ;
  • le tampon horodaté de toutes les mesures brutes ;
  • le dernier état de chaque capteur et le journal des alertes émises, pour qu'elles soient synchronisées après coup.

Peuvent attendre le retour de la connexion : l'entraînement des modèles, les dashboards globaux, les analyses multi-sites et l'archivage. Le critère est toujours le même : ce qui ne tolère pas d'attendre reste au plus près de la source.

PROBLÈME 4 — Retour à l'enseigne de la section 2 : répondre aux trois demandes

On reprend l'enseigne de l'ouverture : 120 magasins, un site marchand, une application mobile, un programme de fidélité, un service après-vente, et une informatique réduite à « applications → base de données → reporting ». La direction a formulé trois demandes :

  1. le chiffre d'affaires de la veille, par région et par catégorie, disponible à 8 h ;
  2. une vue unique du client (caisse, site, fidélité portent trois identifiants différents) ;
  3. la prévision de la demande par produit et par magasin, à partir de trois ans d'historique, alors que la base opérationnelle n'en garde que six mois.

Pour chaque demande : (a) dites pourquoi l'architecture actuelle échoue ; (b) parcourez les cinq couches pour y répondre ; (c) nommez les notions du cours mobilisées. Enfin (d), montrez que les trois réponses partagent le même socle.

CORRIGÉ DU PROBLÈME 4

Demande 1 — CA de la veille à 8 h.

  • Échec actuel : le rapport du soir interroge la base des caisses et ralentit les encaissements (conflit OLTP / OLAP, N16-N19).
  • Couches : sources = caisses des 120 magasins et site ; ingestion = CDC ou export nocturne ; storage = tickets bruts dans le lake, ventes conformes en lakehouse ; processing = nettoyage, transformation, agrégation par région × catégorie × jour ; consommateur = BI (dashboard).
  • Notions : batch et fenêtre de traitement (N20), critère de choix (N22 : un écran lu à 8 h n'a pas besoin de streaming), séparation OLTP / OLAP (N19).

Demande 2 — Vue unique du client.

  • Échec actuel : trois identifiants, trois adresses, trois dates de mise à jour ; aucune couche ne les rapproche.
  • Couches : sources = caisse, site, fidélité ; ingestion = CDC pour suivre les modifications d'adresse ; storage = brut conservé, table client conforme ; processing = nettoyage et rapprochement des identités (règles sur téléphone, e-mail, carte de fidélité), avec une table de correspondance ; consommateurs = BI, Analytics, ML.
  • Notions : qualité relative à l'usage (N25), gouvernance et données personnelles (N26), enrichissement et nettoyage (N34).

Demande 3 — Prévision de la demande.

  • Échec actuel : la base opérationnelle, conçue pour aller vite, ne garde que six mois ; le modèle en exige trois ans.
  • Couches : storage = historique brut des ventes conservé à faible coût dans le lake (niveau froid, N33) ; processing = features (ventes passées, saison, promotions, météo, ruptures) ; consommateur = ML (régression), sorties servies chaque soir aux acheteurs.
  • Notions : Data Lake (N11), AI-driven (N28), exigences croissantes du ML (N29 : features, labels, représentativité), processing (N34).

(d) Un seul socle. Les trois réponses lisent les mêmes tickets bruts et la même table client conforme. Ce qui diffère n'est que la dernière étape : un agrégat pour la BI, une table d'identités pour la vue client, des features pour le ML. C'est exactement la réponse à la question posée en section 2 : remplacer « applications → base → reporting » par une chaîne en couches, sans multiplier les copies ni perdre le contexte, la qualité et la traçabilité.

À RETENIR — la démarche des problèmes du réel
  • Partir des sources et des usages, jamais d'un outil.
  • Chiffrer : volume, croissance, délai exigé, coût. Une décision sans chiffre est une préférence.
  • Le délai exigé choisit entre batch, CDC et streaming ; la coupure possible impose l'Edge.
  • Conserver le brut de ce que les usages futurs pourraient réclamer ; ne préparer à part que la dernière étape.
  • S + C liaisons plutôt que S × C : un socle partagé, gouverné de bout en bout.
